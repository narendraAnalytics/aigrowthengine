SECTION 0 — MARKET REALITY CHECK (researched 2026-08-30)
Is this worth building as a startup? Short answer: yes — but ONLY as described
below. The platform is not the business; it is the acquisition engine for the
services business. Build it that way or it becomes an expensive brochure.
================================================================================

THE TAILWIND IS REAL
  * AI consulting market ~$11–14B in 2026, growing ~24–26%/yr through 2035.
  * Purpose-built AI agent software spend forecast ~$206.5B in 2026 (+139% YoY).
  * SMB AI adoption jumped 22% (2024) → 38% (2026); McKinsey puts SMBs using AI in
    at least one function at 68%, up from 41%.
  * SMBs automating back-office/support report 22–40% cost reduction; ~250% ROI
    claimed within 18 months.
  * India advantage: comparable delivery at a fraction of US/UK implementation cost.
    Typical first meaningful B2B deployment lands $25K–$300K.

THE HEADWINDS ARE ALSO REAL — plan around these, do not ignore them
  * 74% of GenAI pilots never reach scaled production. "Pilot purgatory" is caused
    by evaluation infrastructure, integration depth and governance — NOT model
    quality. Our Phase 3.6 eval harness + Phase 10 TRiSM are the direct answer.
  * ~80% of AI startups are projected to fail by end-2026. The three documented
    killers: commoditization by foundation-model providers, burn before revenue,
    and no data moat.
  * "Thin wrappers around Gemini/GPT" are explicitly called out as extinct. An
    assessment form that pipes text to an LLM IS a thin wrapper.
  * Free AI-readiness assessments already exist from Microsoft, Google Cloud, Cisco,
    Salesforce, SAS, AWS, SAIRA, Elevates.AI. Most exist purely as lead magnets.
    We are entering a crowded lead-magnet category — the assessment alone is NOT
    the differentiator.

WHERE OUR DEFENSIBILITY ACTUALLY COMES FROM
  Ranked by how hard they are to copy:

  1. THE CAPABILITY LIBRARY AS A HONEST CONSTRAINT.
     Every competitor's assessment recommends "AI transformation" in the abstract.
     Ours can only recommend things we have actually built, with a real case study
     attached. The <50% "we can't confidently map this" path is the single most
     differentiating decision in the whole spec. Protect it. Never soften it into
     a generic upsell.

  2. THE GROWTH FLYWHEEL = THE DATA MOAT.
     Projects → outcomes → case studies → richer capability library → better
     matching → better qualified leads. Proprietary data is a moat only when it
     changes product behaviour; here it directly changes what the matcher returns.
     Instrument this from day one: capture every human correction to an AI match
     (Phase 4 "manual score override with mandatory reason"). That correction log
     IS the training asset. Do not treat it as an audit afterthought.

  3. EXPLAINABILITY AS A SALES WEAPON.
     Deterministic backend scoring + the "Why 91?" panel means the model never
     holds business authority. In a market where 74% of pilots die on governance,
     "our AI cannot hallucinate a recommendation, and here is the audit trail"
     closes enterprise deals that a better demo does not.

  4. TRUST/TRiSM AS THE PRODUCT, EVENTUALLY.
     The Investor Room and AI Gateway are not side features — they are the live
     proof of the security capability we sell. We eat our own dog food publicly.

HOW TO MAKE IT SUCCEED — the operating rules
  [ ] PICK ONE VERTICAL FIRST. "Every business" is the fatal generic-startup
      mistake. Choose 1–2 industries where we have real delivery experience
      (e.g. manufacturing back-office, or professional-services finance ops) and
      author the first 10 capabilities ONLY for those. Horizontal comes later.
  [ ] SELL THE OUTCOME, NOT THE ASSESSMENT. The assessment is free and fast; the
      revenue is the pilot. Target: assessment → consultation ≥20%, consultation
      → paid pilot ≥25% (FinalRoadMap §8).
  [ ] PRICE IN THREE TIERS. Paid diagnostic/discovery sprint (small, fast, proves
      value) → fixed-price pilot → retained "Automation as a Service" (AaaS)
      monthly. AaaS is the fastest-growing model in this space in 2026 and turns
      project revenue into recurring revenue. Separate access (subscription) from
      consumption (usage/credits) so margins stay safe as LLM spend scales.
  [ ] GET 3 REAL CASE STUDIES BEFORE POLISHING THE PLATFORM. The flywheel is dead
      without them and no amount of frontend work substitutes. Deliver the first
      projects manually if necessary — the platform's job is to make project 4–40
      repeatable, not project 1.
  [ ] DEFINE THE CONTROL BUDGET. No GPU burn here (we call Groq), but token
      spend, Neon, Vercel and Cloud Run add up. Track cost-per-assessment from
      Sprint 3; it must stay well under the value of a qualified lead.
  [ ] DO NOT BUILD THE INVESTOR ROOM UNTIL YOU ARE ACTUALLY RAISING. It is Phase 7
      for a reason. Traction first, data room second.
  [ ] KILL CRITERIA. If after Sprint 7 (MVP validation with real users) the
      assessment → consultation rate is under ~10% and no paid pilot has closed,
      the problem is positioning or vertical choice, not the code. Re-pick the
      vertical before writing Phase 6+.

THE ONE-SENTENCE POSITIONING TO DEFEND
  "The only AI assessment that will tell you when we cannot help you — because
   every recommendation is backed by something we have already shipped."

  - chat.completions.create params (from Groq docs — verified 2026-08-31):
      model: "openai/gpt-oss-120b"
      reasoning_effort: "medium"          (low=simple classify, high=nuance)
      reasoning_format: "hidden"          (REQUIRED with JSON mode or reasoning
                                           contaminates content)
      temperature: 0.4                     (consistency)

        name: "assessment_signals", strict: true, schema: <generated> } }
  - Strict-mode schema rules: EVERY property in `required`,
    additionalProperties:false everywhere, optional field => type ["T","null"].
    Streaming + tool use unsupported with structured outputs.
  - KNOWN RISK (Groq community report): 120b sometimes ignores the schema.
    MITIGATION: keep parseLeadSignals()/Zod as the real guarantee; on Zod
    failure do ONE repair-prompt retry ("your last reply did not match the
    schema, return only valid JSON"), then fail closed => status "failed".
  - Generate the JSON schema from a Zod schema (zod-to-json-schema) or hand-write

STEP 2 — the deterministic matcher   src/lib/matching/match-capabilities.ts   (+ test)
  Pure, versioned (MATCHER_VERSION "1.0.0"), NO model call.
  Input: problem_types[] (from Groq, filtered via filterKnownCapabilityIds-style
         validation against PROBLEM_TYPES), industry (from the form).
  For each capability in CAPABILITIES:
    ptScore  = |problem_types ∩ cap.problemTypes| / |problem_types ∪ cap.problemTypes|
    indScore = industry ∈ cap.industries ? 1 : 0
    confidence = clamp01( 0.65*ptScore + 0.35*indScore )
  Return capabilities sorted by confidence desc, each with
  classifyMatch(confidence) (match.ts) + a rank. Top 3.
  bestConfidence < 0.50  => no_confident_match path.
  Phase 8 replaces this with pgvector hybrid retrieval behind a flag.

STEP 3 — the pipeline   src/server/assessment/run-assessment.ts   (+ test w/ mocked Groq)
  submit answers (validated by submitAssessmentRequestSchema)
   -> 1 Groq call: { problem_types[], signals{7 factors}, summary }
   -> validate problem_types against PROBLEM_TYPES (drop unknowns; empty => try
      "no_confident_match" sentinel)
   -> matchCapabilities(problem_types, industry) -> ranked matches
   -> signals.solution_fit.level = matchClassToSignalLevel(classifyMatch(best))
      (rationale = "capability match: <name> at <confidence>")
   -> parseLeadSignals(signals)  (Zod; on fail -> repair retry -> fail closed)
   -> computeLeadScore(signals)  -> { score, band, breakdown[7], modelVersion }
   -> persist (Drizzle, transaction):
        assessments        (answers jsonb, status, organization_id NULL = personal)
        assessment_results (problem_types, industry, lead_score, score_band,
                            scoring_model_version, breakdown jsonb, summary,
                            no_confident_match)
        capability_matches (one row per ranked match)
   -> return assessment id
  status flow: submitted -> analyzing -> scored | needs_expert_review | failed
  Never send raw contact PII to Groq (the questions don't collect any yet — keep
  it that way for the slice).
